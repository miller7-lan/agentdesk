# 任务分配方案：按能力派活 + 按实测调整（2026-11-17）

> 结论：不再把「哪个 AI 干哪一步」写死，而是**规划时只说每步需要什么能力，由调度器按候选顺序挑当前可用、额度够的 AI**；候选顺序和额度阈值先按经验定，再按每个任务实际消耗的额度调整。第一阶段已经实现，见文末「实现状态」。

## 1. 为什么不用固定流水线

之前的设想是每个任务都走「Antigravity 侦察 → Claude 规划 → Antigravity 简报 → Codex 改代码 → 测试 → Grok 审查 → Antigravity 汇总 → Claude 验收」。问题是：

- **小任务被拖慢、更费额度**：改一行配置也要调用 8 次模型，多数调用没有必要。
- **一处卡住全部卡住**：Grok 额度用完，审查这一步就没人做，整个任务停下。
- **最优分工未知**：哪家更擅长侦察、哪家审查更准，只能靠实测，写死就没法调。

## 2. 新方案

### 2.1 按能力派活

Claude 规划时给每一步标一种能力，主控按候选顺序挑第一个「已配置、没掉登录、额度没用尽」的 AI：

| 能力 | 做什么 | 能否改文件 | 默认候选顺序 | 为什么这样排 |
|---|---|---|---|---|
| 规划 `plan` | 拆任务、定验收标准 | 否 | Claude → Codex | Claude 统筹；Codex 仅在 Claude 不可用时兜底 |
| 侦察 `scout` | 读代码 / 日志 / 文档，写简报 | 否 | Antigravity → Gemini → Grok | 读得多、写得少，放在不太紧张的额度上；Claude 不参与 |
| 改代码 `implement` | 按简报修改 | **是** | Codex → Grok Build → Antigravity | 先给 Codex，额度用尽或掉登录时按此顺序降级；永不降到 Claude；同一步只有一个成员在写 |
| 审查 `review` | 看改动、找问题 | 否 | Grok → Antigravity → Gemini | 和改代码的不是同一家，交叉检查；Claude 不参与 |
| 查资料 `research` | 仓库外的信息 | 否 | Grok → Antigravity → Gemini | Grok 能联网搜索；Claude 不参与 |
| 升级 `triage` | 任务卡住时判断下一步 | 否 | Claude | 只有组长决定重试、返工、带风险接受或终止 |
| 验收 `accept` | 看摘要判断是否达标 | 否 | Claude | 组长把关，只读摘要 |

这是**严格执行**而不是偏好：`routing.js` 会拒绝任何把 Claude 放进 `implement` / `review` / `scout` / `research` 的配置；Claude 的额度也只留给 `plan` / `triage` / `accept`。规划者可以建议具体由谁做；只要那个 AI 在该能力的候选里且可用，就按建议来，但不能绕过这条限制。

### 2.2 按任务大小分档

由 Claude 在规划时判断（提示词里已写明规则）：

| 档位 | 例子 | 步骤 |
|---|---|---|
| 小 | 改配置、修一个明确的 bug、问答 | 1 步改代码（必要时加审查） |
| 标准 | 跨几个文件的功能修改 | 改代码 → 审查 |
| 复杂 | 不熟悉的模块、大改动 | 侦察（写简报）→ 改代码 → 审查 → 验收 |

另外，单步的小任务在群聊里可以直接点名 Codex 或某个审查类 AI，不经过 Claude 规划；Claude 不能被点名执行实现。

### 2.3 免费检查优先

测试和构建由主控在最后自动跑，**不花任何模型额度**，所以规划里不为它们单独安排一步。模型审查只在改动大或有风险时安排。

### 2.4 按额度让位（订阅制）

订阅制下有限的是**额度**（5 小时窗口和每周窗口的已用百分比），不是 token。主控每 2 分钟读一次各家额度：

| AI | 用量超过「让位线」后 | 用量超过「停用线」后 | 默认 |
|---|---|---|---|
| Claude | 只做规划、升级诊断和验收 | 不再派活 | 60% / 95% |
| Codex | 只做改代码 | 不再派活 | 70% / 95% |
| Grok / Gemini / Antigravity | — | 不再派活 | 95% |

规划时，各家的已用百分比也会交给 Claude，让它把读代码、查资料、审查交给额度多的 AI。阈值在配置的 `quotaPolicy` 里可改。

### 2.5 额度用尽或掉登录时自动换人

某个 AI 在执行中报「额度用尽」或「未登录」：

1. 主控暂停使用它（额度 30 分钟，登录 6 小时，或直到你处理）。
2. 这一步交给同一能力的下一个候选，记录一条「改派」事件。
3. 改代码的步骤只会改派给能写的 AI。
4. 没有可用候选时**不降级、不借给别的角色**：只要该能力还有已配置的候选，任务保持排队，detail 为 `executor_waiting:<能力>`，约 1 分钟后重试；Claude 的规划、升级和验收同样等待，绝不交给 Codex 代做。
5. 只有该能力完全没有已配置的候选时才报 `no_executor`。

按人日额度上限也走等待路径：某人的候选全部超过当日上限时，任务等到本地次日零点，detail 为 `owner_quota_cap`，同一等待期只记一条事件。

### 2.6 按实测调整候选顺序

每个任务记录它**消耗了各家多少额度**（开始和结束时各读一次已用百分比，记差值；包含同一账号在这段时间里的其他使用）。token 用量也记录，只作参考。任务的 `metrics` 现在同时记录步数、各 CLI 调用次数、改派次数、测试失败、审查冲突、返工和升级轮数、首轮是否通过；`ad report` 汇总这些数字，`ad benchmark` 对照单干和多 agent 两组（操作见 [BENCHMARK.md](BENCHMARK.md)）。积累 20～30 个真实任务后，按下面的问题调整 `routing`：

- 侦察交给 Antigravity 和交给 Gemini，Codex 后续改代码的返工次数有没有差别？
- 审查交给 Grok，漏掉的问题（之后测试或你自己发现的）多不多？
- Claude 的额度主要花在规划、验收还是被改派过来的活上？平均每个任务花掉 Claude 几个百分点？
