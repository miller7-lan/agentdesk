# 群聊任务断开与长时间停顿：诊断和修复方案

日期：2026-11-19。时间统一为北京时间（UTC+8）。

范围：任务 `af299a1c` 的任务事件、各步骤 CLI 日志、VPS2 systemd 日志、本机应用与 Bridge 日志，以及当前功能分支源码。本文仅提出方案，不代表已实施下述调度、连接或性能改动。此前已修复的文件写入转发、节点圆点和常驻连线问题另行标注。

## 一、结论与证据

耗时来自多个独立原因。不能把服务重启、CLI 超时、额度等待、模型长时间无输出统称为网络断线。

| 原因 | 已取得的证据 | 影响与证据边界 |
| --- | --- | --- |
| 主控反复停止、启动 | 17:25–22:08 的 systemd 记录有 9 次停止/启动；其中 1 次发生在本任务创建前。19:30:19 停止至 19:38:22 启动约 8 分钟；21:48:50 至 21:58:45 约 10 分钟 | 服务空窗期间无法调度。源码的恢复逻辑会重新排队运行中步骤；任务确有 `recovered` 和重复 `started`。日志不能单独证明是谁或哪个程序发起停止，不能直接归为服务崩溃 |
| 组长不可用、额度等待 | 任务事件中有 12 次 `triage_unavailable`、31 次 `triage_unavailable:quota`；17:48 首次侦察失败，19:12 才开始执行重排诊断 | 此阶段大部分时间在等组长。不可将整段时间都精确归为额度耗尽，因为前 12 次没有相同原因标签 |
| 文件写入接口曾丢字段 | `impl-deploy` 和 `impl-backend` 日志分别有 10、6 处 `invalid_content` 文本记录；审查通过原始清单哈希确认文件没有落盘 | 记录数不是独立失败请求数。步骤仍被标完成，后续才发现交付缺失，造成返工。当前功能分支和 VPS2 的 `mcp.js` 已包含 content/encoding/version 等转发修复；本次 fix 的写入回执及本机哈希已证明写入恢复 |
| CLI 与主控超时不一致 | Antigravity 模板传入 `--print-timeout 10m`；主控单次默认 `cliTimeoutMs=900000`，即 15 分钟。scout、fix、rework 日志均出现 print timeout；22:36 返工开始，22:46 又续跑同一会话 | CLI 自行在主控超时前退出；用户看到步骤再次开始，却不容易知道是续跑。并非模型始终在有效工作，也不是每次都从头规划 |
| 模型选择曾失败 | 首次 scout 使用 `gemini-4-hydrogen` 并以 `cli_exit_1` 失败；当时可用清单与该模型不一致，诊断后改用清单内模型重试 | 模型选择不一致已证实；仅凭退出码无法严格证明它是首次退出的唯一原因 |
| 工具调用和串行探索开销 | CLI 日志统计：fix 有 113 个完成的工具事件，累计记录耗时约 753 秒，中位数 3.5 秒、单次最大 44.3 秒；早期 impl-deploy 中位数约 0.5 秒。返工有反复列家目录、桌面和部署目录的记录 | CLI 计时可能包含工具包装、排队或网络；累计时间可能有重叠。尚无同请求端到端 tracing，不能断言慢在磁盘或某条网络线路 |
| 交付不完整导致再次返工 | 首轮验收发现防火墙把回环 worker 当成公网遗留监听，同时把预期的 443 前置监听当冲突；其后又执行了一轮验收，再进入 rework | 文件成功写入不等于实现正确。验收并未全部通过；不能直接上线 VPS1 |
| 观察界面不能充分解释等待 | 应用有 `sleeping` 状态；Bridge stderr 有无时间戳的 `ECONNRESET`。活动读取还存在 300 条记录上限，超过后丢弃新增条目 | sleeping 属于设计的空闲休眠，不能算异常断线。无时间戳的 reset 不能准确对应本任务停顿；300 条上限是源码风险，尚未证明本次每一步均触发 |

补充：步骤日志中较长的无输出区间只能证明“没有新的可见事件”。进程存在、TCP 为 ESTABLISHED 都不能证明模型仍在有效推进。

## 二、P0：先避免重复消耗和假完成

首批改动以 `65da1ea` 为基线，在独立群聊分支复用维护模式、项目快照及原会话续跑。新调用记录在调度时写入原成员、模型、阶段和尝试编号，结束时补上状态、耗时和 CLI 已报告的用量。服务重启只记录何时观察到中断。旧任务的近似统计继续可读。旧任务恢复执行后，新调用统计只计可验证的新记录。

快照写入步骤会附上 Worktree 的 Git 基线、HEAD、跟踪文件差异哈希、已观察到的文件名和本机写入回执，方便接手者先检查原成果。未跟踪文件只记录文件名，差异哈希不能用于证明完整工作区版本。具有本机副作用的快照步骤在异常退出且结果未知时转入人工核对，避免从原会话或新模型重复提交操作。

### 1. 部署前排空执行中的任务

- 增加维护状态：停止领取新步骤，已有步骤执行到安全边界后再更新主控；界面显示等待结束的任务列表。
- 安装流程默认检查 running/applying/testing；普通更新禁止直接重启。紧急重启记录原因、操作者/来源、受影响步骤。
- 将长期 CLI 子进程与可重启的 API/调度服务分离，保留执行租约、会话 ID 和可恢复检查点。此项需要单独设计，不能仅靠重启后的再次运行冒充恢复。
- 对写入使用 request_id、目标版本和回执；重启后先查请求结果，确认未知状态后再决定是否重试。

验收：在测试环境的长任务执行中请求维护，任务不中途重跑；模拟调度服务重启，已确认写入不重复执行，未知写入不自动覆盖。

### 2. 用落盘证据判定完成

- 为 MCP 定义统一参数 schema 和转发契约；覆盖 content、encoding、version、destination 等所有实际参数，防止再次静默丢字段。
- 文件修改步骤返回结构化交付清单：本机目标路径、修改前版本、修改后哈希、写入回执、验证命令与结果。
- 主控核对目标文件版本；存在未解决写入错误、缺失交付或只有 scratch 文件时，步骤进入 blocked/failed，不向下游宣称完成。
- 把“成员自报完成”和“已验证交付”保留为两种状态。

验收：模拟写入工具拒绝、版本冲突和只写 scratch，三者都不能进入完成；正常写入回执与本机哈希一致才允许下游执行。

### 3. 统一 CLI 时间预算并展示续跑

- 从同一配置生成 CLI 内部时限和主控外层时限，外层保留退出、保存和取消的宽限；不再散落固定 10m/15m。
- 先核实当前 CLI 版本支持的超时、恢复参数，再决定预算；不要把无限延长时间当作修复。
- 将 print_timeout、主控总时限、工具超时、网络断线、登录失效、额度不足分别编码。
- CLI 输出超时且已有有效会话时，保存检查点、当前文件版本和未完成事项；有限次数续跑同一会话，界面显示原因、次数与已花时间。
- 无新事件时显示“距最后事件 X 秒”，由最后事件类型区分模型等待、工具执行和资源等待；无证据时不声称仍在思考。超过策略阈值才提供诊断/停止入口。

验收：用假 CLI 模拟内部超时，准确显示 timeout 与续跑次数；从原会话恢复且不重复已确认写入。网络断开与额度错误不再都显示 cli_exit_1。

## 三、P1：减少不做事的等待

### 4. 额度与模型就绪检查

- 派发前校验模型确实在当前账号目录内；保存派发时使用的目录版本及模型映射，禁止静默换成未列出的 ID。
- 任务开始前核对组长规划、诊断和验收所需额度；保留诊断/验收预算，避免成员执行完成后无人接手。
- 已知额度恢复时间时，调度到相应时间并增加轻微抖动；未知时使用有上限的退避。额度状态没有变化时不重复调用付费诊断，也不反复追加等价等待事件。
- 提供准确的等待原因、最早重试时间、人工操作入口。是否允许其他模型承担组长职责单独作为产品策略，不能擅自突破现有分工约束。

验收：模拟额度耗尽一小时，等待期间不启动重复模型调用；恢复一次后只派发一次。过期模型在执行前被明确拒绝。

### 5. 减少全量读文件和重复寻路

- 上下游传递结构化交接：目标绝对路径、已读文件及版本、待修行号、已完成步骤、验证结果和剩余问题；返工直接携带这些内容。
- 对稳定文件做任务级、带版本的只读快照，优先按行区间/关键词读取；修改前仍向本机重新校验版本。
- 将相互独立的只读请求批量处理，设置有界并发；写入、版本校验和依赖步骤保持有序。
- 大文件传输通过受控工件/补丁接口完成，避免模型反复把整个文件编码、解码、复述。不可无审核地覆盖本机刚发生的修改。
- 工具调用增加 request_id 和分段计时：模型发起、主控接收、Bridge 收到、文件操作、返回完成。先测基线，再决定是否需要线路或文件系统优化。

验收：固定同一批文件做前后对照，记录端到端 p50/p95、调用次数、读取字节、模型输入量和任务总时长；目标为重复全量读取和寻路请求减少至少一半，正确性检查不退化。当前尚未有可承诺的总耗时提升比例。

### 6. 简化审查与返工

- 区分计划里的审查步骤和主控最终验收，消除目的相同、输入无变化的连续验收。
- 将验收 findings 转为明确修复清单，列出文件、行号、复现条件、期望行为和验收命令；返工保留原任务约束及目标目录。
- 为此次真实发现建立回归用例：回环监听不算公网遗留监听、443 预期服务不算冲突、共享 Reality 私钥与订阅公钥一致、SNI 生产路径缺失必须报错。
- 确定性检查先运行，模型审查再判断剩余设计风险；不接受“未读取实现，仅依据文档推断通过”。

验收：上述缺陷在测试中稳定复现并修复；同一轮未改文件时不会重复验收，未解决 blocker 不会给通过结论。

## 四、P1：让连接和进度可诊断

- Bridge、SSH、CLI、调度状态全部记录 UTC 时间、task_id/step_id、request_id、路由、重试次数和脱敏错误码。现有无时间戳的 reset 日志无法回溯补齐。
- 将应用到 VPS2、VPS2 到 Bridge、VPS2 到模型供应商分开显示；保留主机指纹校验，不自动放宽 SSH 安全设置。
- 把正常 idle/sleeping 与连接失败区分；客户端休眠或重连不应中断服务器上已领取的任务。
- 独立心跳显示服务/执行器存活和最后实际活动，不伪造模型进度。
- 活动接口按游标增量获取，历史按需加载；超过单页上限时保留最新事件并明确还有历史，不能丢掉最新进度。
- 常驻虚线表示未查看的已完成步骤。原有持久化 60 条截断已在另一提交移除；不得把暂时离开视野等同于已读。

验收：可控注入三条链路各自断线、正常空闲休眠、服务重启、模型超时，界面分别显示准确原因。日志足以关联一次请求的各段耗时。300 条以上活动仍能看到最新完成事件。重连不重复提交任务。

## 五、执行顺序与回滚

1. 当前任务结束后再进入维护窗口；先备份配置、SQLite 一致性备份、应用和 Bridge 副本。
2. 先实施落盘回执、错误分类和可观测性，建立测试基线；随后统一时限和有限续跑。
3. 再处理额度/模型校验、结构化交接、批量读取和验收去重。长期 CLI 执行与调度服务解耦作为后续独立变更。
4. 按仓库要求运行 Node 测试及受影响平台 CI；连接/恢复逻辑用假 CLI 和断线注入验证，另用一个不修改真实项目的小任务做端到端验收。
5. 先部署 VPS2，再更新本机 Bridge 和应用；每端分别验证，不在运行中强制滚动重启。
6. 配置、代码、数据库变更分别有回滚路径。发现未知写入或不兼容 schema 时先暂停任务核对，不能自动回放写操作。

完成标准：同样的长任务不因发布重启而重跑；写入失败不再被当成功；超时和额度等待有准确状态与恢复策略；最新活动不丢失；耗时改进由测量而非动画变化证明。
